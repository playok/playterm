# 릴리스 검증과 변경 내역

릴리스 담당자는 후보의 변경 범위, 실제 지원 조합, 최종 패키지와 서명 상태를 확인한다. 배포하지 않은 master 변경을 이전 릴리스 기능으로 표시하지 않는다.

## 사용자 변경 내역 준비

1. `python scripts/release-notes.py --draft --tag vX.Y.Z --output target/release-draft.md`로 직전 태그부터 HEAD까지의 커밋 후보와 네 개 사용자 설명 섹션을 만든다. 이 초안은 게시용이 아니다.
2. 후보 범위를 검토하고 `docs/releases/next.md`와 커밋·PR·이슈를 대조한다. 사용자가 경험하는 기능과 수정 조건, 설정 마이그레이션, 재시작 영향, 알려진 제한을 쓴다. 해당 없는 항목은 명시한다.
3. 검토한 내용을 `docs/releases/vX.Y.Z.md`에 넣고 TODO·UNRELEASED 표시를 제거한다. 버전 변경과 함께 커밋한 뒤 그 커밋에 태그를 붙인다. 태그 뒤 master 변경은 넣지 않는다.
4. 릴리스 워크플로는 `git show <태그>:docs/releases/<태그>.md`에서 설명을 읽는다. 파일·필수 섹션이 없거나 초안 표시가 남으면 게시를 중단한다. 비교 링크는 해당 태그의 직전 조상 릴리스부터 생성한다.
5. 패키지 표, 실제 서명·공증 안내, 체크섬을 빌드 결과에서 뒤에 붙인다. 앱 내 업데이트 창에는 Downloads 앞 사용자 변경 내역을 읽기 쉬운 색상으로 표시하고, 전체 표·체크섬은 릴리스 페이지에서 확인한다. 이전 릴리스 형식은 기존 본문을 표시한다.

## 최종 파일 검증

- Windows: `package.ps1 -BothVariants`는 같은 아키텍처의 동일 빌드에서 기본 미압축 ZIP과 `-upx.zip`을 만든다. 각 복사본의 UPX 처리 뒤 코드 서명하고, 최종 ZIP을 풀어 Authenticode 상태·게시자·타임스탬프를 검사한다. `-CodeSign`이면 유효하지 않은 체인이나 타임스탬프 누락은 실패한다. `.verification.json`은 CI 아티팩트에 보존한다.
- macOS: 최종 ZIP에서 앱을 꺼내 `codesign --verify --deep --strict`를 실행한다. 공증 경로에서는 그 사본에 `stapler validate`, `spctl --assess`도 실행한다. 해당 검증을 통과한 뒤에만 게시 작업으로 넘어간다.
- 최종 ZIP의 SHA-256을 생성한다. Windows 체크섬의 Ed25519 서명은 기존 앱 공개 키와 검증한다. Authenticode와 업데이트용 Ed25519 서명은 각각 별도로 확인한다.
- 서명 인증서·공증 계정이 없으면 unsigned/ad-hoc 상태를 그대로 알린다. 정식 서명 배포를 표방할 수 없다. SmartScreen 평판이나 백신 오탐 해소를 보장하지 않는다.
- 미압축 기본 패키지는 기존 자동 업데이트 파일명을 유지한다. 기존 압축 패키지와 새 `-upx` 패키지 사용자도 다음 자동 업데이트에서 미압축 기본 패키지로 전환한다.

## 승인과 남은 환경

[호환성 표](compatibility.md)와 [부하 시험](stress-testing.md)의 필수 조합을 확인한 뒤, 깨끗한 각 OS/아키텍처에서 실제 다운로드→압축 해제→첫 실행을 검증한다. 크로스 컴파일 성공은 실제 실행 결과로 기록하지 않는다.

#192의 정식 코드 서명·공증에는 관리자가 준비한 Windows 코드 서명 인증서와 Apple Developer ID/공증 계정, macOS 실행 장비가 필요하다. 현재 저장소의 지원 경로를 재사용한다. 비밀 값은 로그·문서에 남기지 않는다. 담당자가 다음 서명 릴리스 후보를 만들기 전에 인증서 준비와 플랫폼 검증 일정을 확정한다. 확정되지 않은 날짜를 완료 예정일로 쓰지 않는다.
