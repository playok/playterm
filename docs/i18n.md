# UI language and connection encoding

UI language and remote character encoding are independent settings.

## Resource layout and adding a language

All translated UI text, help and transport errors live in
`crates/playterm-i18n/locales/`. `en.toml` is the canonical key/argument schema;
`ko.toml`, `ja.toml` and `zh-cn.toml` contain complete Korean, Japanese and
Simplified Chinese translations. The application contains keys, not sentence pairs.

To add a language, add a UTF-8 TOML file in that directory and rebuild. For example,
`fr.toml` can begin with:

```toml
[locale]
code = "fr"
name = "Français"
aliases = ["fr-FR"]

[text]
"common.close" = "Fermer"
"language.follow_system" = "Suivre le système"

[format]
"app.broadcast.typing_into_all_tabs_other" = "Saisie dans tous les onglets · {others} autres"
```

No UI code, enum variants or registration list needs editing. The build discovers
catalogs, generates `Language::ALL` and embeds the text. The language picker uses
the native names in `[locale]`. Locale codes use lowercase hyphenated forms, such
as `pt-br` or `zh-hant`; aliases are normalized and must be unique. The filename is
for maintainers; `[locale].code` is the stable identifier used in settings.

Missing entries in an additional language use English **per message**. Omit an
unfinished entry rather than using an empty value. Unknown keys, duplicate locale
codes/aliases, malformed placeholders and mismatched arguments fail the build.
The shipped languages are English, Korean, Japanese and Simplified Chinese; the
example is not a shipped French translation. Review a new catalog's wording and font coverage before release.

## Translation rollout

| Stage | Languages | Status / rationale |
| --- | --- | --- |
| Baseline | English (`en`), Korean (`ko`) | Project default and current user base |
| Phase 1 | Japanese (`ja`), Simplified Chinese (`zh-CN`) | Implemented; reach nearby Asian users first |
| Phase 2 | Spanish (`es`), Brazilian Portuguese (`pt-BR`) | Next expansion beyond English-speaking users |
| Phase 3 | German (`de`), French (`fr`), Traditional Chinese (`zh-TW`) | Add when sustained contributors or user demand are confirmed |

The language picker includes only implemented catalogs. Phase 2 and 3 are a roadmap,
not fallback-only language choices. Each phase should include complete translations,
placeholder checks and native UI/font review before release.

Japanese matches `ja-JP` as well as `ja`. Simplified Chinese uses the persisted code
`zh-cn`, with `zh-hans` and `zh-sg` aliases (including their more specific variants).
It deliberately does not claim bare `zh`, `zh-TW`, `zh-Hant`, `zh-HK` or `zh-MO`;
these fall back to English until an appropriate catalog is available.

## Writing UI code

```rust
use playterm_i18n::{t, tr};
ui.button(t!("common.close"));
ui.label(tr!("app.broadcast.typing_into_all_tabs_other", others = count));
```

Use `[text]` for literal text (`t!` returns `&'static str`) and `[format]` for messages
with named arguments (`tr!` returns `String`). Add new stable, descriptive keys to
all shipped catalogs together. Keep keys unchanged when wording changes. Group new
keys by feature, and reuse a common key only when its meaning is the same.

Supply `tr!` arguments explicitly in alphabetical name order. The generated macro
signatures reject unknown keys and missing, extra or misspelled arguments at compile
time. Expressions are evaluated once. New messages should use meaningful argument
names, such as `host` and `count`; migrated positional arguments retain `arg0`, etc.

Translations may reorder or repeat named arguments but must retain the same set.
Use `{{` and `}}` for literal braces in `[format]`; `[text]` braces are literal.
Arguments are inserted as plain text and never reinterpreted as template syntax.
Keep Rust-specific formatting in the caller, e.g. `error = format!("{error:#}")`,
so translation files contain no Rust expressions or format specifiers. This is
named interpolation, not an ICU plural/date/number formatting engine; use separate
message keys when different grammatical forms are needed.

Protocol tokens, file names, encoding names and test fixtures do not need translation.

## Language selection and compatibility

`playterm-i18n::Language` owns locale resolution, runtime selection and serialized
codes. `playterm-config` re-exports this type. Internal numeric IDs are generated
and are never persisted; adding or sorting catalogs cannot change saved preferences.

New or missing preferences use `system`. Windows, macOS and Unix OS lookup uses
`sys-locale`, cached for the process lifetime. Matching normalizes case, underscores,
encoding/modifier suffixes and then tries progressively less-specific tags:
`zh_Hant_TW.UTF-8` → `zh-hant-tw` → `zh-hant` → `zh`. Unavailable languages fall back
to English. Explicit choices override OS detection and survive restart; existing
`ko`/`en` settings remain compatible. An unknown saved code also falls back to
English rather than causing the settings file to be treated as corrupt.
Restart the app after changing the OS language.

## Validation

```sh
cargo test --locked -p playterm-i18n
cargo test --locked --workspace
```

Tests cover locale matching, persisted codes, generated language registration,
English fallback, reordered/repeated arguments, literal braces, single evaluation
and malformed catalogs. Compile-fail doctests verify unknown keys and invalid
argument lists. The workspace's UI tests protect the existing Korean flows.
Run the native application with an isolated `PLAYTERM_CONFIG_DIR`, check language
preview/cancel/save and restart, and inspect long translations and font coverage.

## Connection encodings

`playterm-term::Charset::ALL` is the shared list used by the profile editor.
The streaming decoder preserves partial multibyte sequences between reads;
the input encoder replaces unrepresentable characters with `?`. Profiles retain
the selected charset across restart. `Charset::from_label` resolves supported
WHATWG encoding labels and common numeric Windows code pages for importers.
WHATWG aliases apply (for example ISO-8859-1 resolves to Windows-1252).

Supported families: UTF-8, CP949/EUC-KR, Shift_JIS, EUC-JP, GBK, GB18030, Big5,
Windows-1250 through 1258, Windows-874, IBM866, KOI8-R/U, Macintosh, Mac Cyrillic,
and ISO-8859-2/3/4/5/6/7/8/8-I/10/13/14/15/16.

Automatic detection remains limited to UTF-8 and CP949. Other encodings must be
selected explicitly. UTF-16 and ISO-2022-JP are deliberately excluded: the terminal
transport and control parser require ASCII-compatible, non-stateful encodings.
RDP uses its own protocol text handling and does not use this setting.
